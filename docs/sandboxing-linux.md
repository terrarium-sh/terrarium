# Linux sandboxing

The supervisor starts the VM worker and, with networking enabled, the network
broker under Bubblewrap, which ships inside the `terra` executable. Every role
also runs under seccomp filters; [host process sandboxing](sandboxing.md)
covers what each role holds.

## Process layout

```text
terra (CLI)                 your user, unconfined
└─ terra __supervisor       role filter + allowlist once the workers
   │                        start; holds the run lock and listeners
   ├─ bwrap ─► __vm         own user, PID, mount, IPC, UTS and
   │                        network namespaces; role filter and its
   │                        allowlist; /dev/kvm, read-only
   │                        box state with writable logs and
   │                        disks; shares
   └─ bwrap ─► __network    own user, PID, mount, IPC and UTS
                            namespaces; host network; role filter
                            and its allowlist; no /dev, no /tmp

__vm ◄── socket pair (fd 7) ──► __network
__supervisor ── startup channel (fd 8) ──► __network
__supervisor ── run lock (fd 3) ──► __vm
__supervisor ── agent and control listeners (fd 10, 11) ──► __vm
terra (CLI) ── agent and control sockets ──► __vm
```

## Namespaces and capabilities

- Both workers get separate mount, user, PID, IPC and UTS namespaces and drop
  all capabilities. The VM also gets a private network namespace, so its native
  sockets cannot reach host networking; the broker keeps the host network
  namespace.
- The broker gets no `/dev` device nodes and no `/tmp`. It does get `/proc`,
  where `/proc/net` lists the host's connections and Unix socket names.
- The launcher clears the inherited environment and forwards only diagnostic and
  worker metadata. Guest environment grants travel in the boot plan; broker
  policy and listener grants arrive on a supervisor-controlled startup channel
  that VM requests cannot alter.

## Seccomp filters

- Bubblewrap installs each worker's role filter after namespace setup and before
  exec; the worker installs its compiled-in syscall allowlist as it starts. The
  supervisor installs its own lifecycle filter and allowlist.
  Allowlists are generated by statically scanning each role's code
  ([host sandbox policy](sandbox-policy.md)).
- Workers stay in the host session, so the role filters and allowlists deny the
  `TIOCSTI` and `TIOCLINUX` terminal-injection ioctls.
- The broker shares the host network namespace, where abstract Unix sockets
  (such as an X11 display) and host netlink live. Its filters allow only IPv4
  and IPv6 sockets and Unix stream socket pairs, and deny `listen`; the
  supervisor reads host interface addresses for it.

## Lifetime

- `host.pid` names the VM in the host PID namespace and `supervisor.pid` the
  process owning box lifetime. Workers cannot rewrite these through their
  filesystem grants. Stop and failed startup clean up the whole process tree.
- The VM holds a duplicate run-lock descriptor, so supervisor death cannot let
  another boot reuse the disks before the old VM exits. The lock is cooperative:
  compromised native VM code can unlock its own box.
- Broker failure after startup leaves the VM and agent running with networking
  unavailable; there is no reconnect or fallback to direct networking.

## Validation

The built-in launcher targets the statically linked musl release executable.
Native KVM and negative enforcement tests are required per architecture.
